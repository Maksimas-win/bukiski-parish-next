# Памятка владельцу: bukiski-hram.net

Коротко и без технических подробностей. Полная инструкция — [MAINTENANCE.md](../MAINTENANCE.md).

## Два сайта — два репозитория

- **bukiski-hram.net** → репозиторий `bukiski-parish-next` (этот). Основной сайт на шести языках.
- **bukiski-hram.org** → репозиторий `bukiski-hram-org`. Сайт на четырёх языках, инструкция GPM и источник расписания для обоих сайтов.

## Как сайт обновляется

Вы меняете файлы в ветке `main` (обычно через pull request). GitHub сам собирает сайт, проверяет его и отдаёт Hostinger. Через одну-две минуты изменения видны на сайте. Ничего заливать по FTP не нужно — и не нужно: автоматика перезапишет.

Расписание берётся из приходского Google-календаря: правите календарь — через несколько часов (четыре обновления в сутки) сайт его подхватит. На сайте .org — в течение часа.

## Что менять и где

- Телефон, адрес, время открытия, соцсети → `content/settings.json`.
- Тексты кнопок и надписей → `content/locales.json`.
- Служба, которой нет в календаре (или стоит без времени) → `content/schedule-additions.json`. Лучше всё же поставить службу с временем в Google-календаре: тогда она появится и на .org.
- Фотографии → `content/photos.json` и папка `assets/img/parish/`.
- Ответы помощника на сайте → `assets/js/assistant/knowledge.js` (и такой же файл в репозитории .org).
- Раздел «1,2 % GPM» (сроки кампании, год, дата проверки VMI, суммы проектов) → `content/gpm/config.json`; тексты шести языков → `content/gpm/<язык>.json`. Подробнее — `docs/EDITING.md`, раздел «1,2 % GPM».

## Если пришло письмо от GitHub

1. **Письмо о неудачном запуске «Export production site…»** — изменение не опубликовалось, сайт показывает прежнюю версию. Откройте запуск по ссылке в письме, посмотрите красный шаг. Чаще всего это ошибка в правке: исправьте и отправьте снова.
2. **Письмо об issue «Мониторинг: …»** — автоматическая проверка нашла сбой на одном из сайтов. Откройте issue: в нём написано, что именно не прошло.
   - Оба сайта не отвечают — почти наверняка проблема у Hostinger; подождите и проверьте hPanel. Ничего переустанавливать не нужно.
   - «schedule-freshness» — расписание не обновлялось больше двух суток: загляните в репозиторий .org, вкладка Actions; обычно это временно недоступный Google-календарь.
   - «не виден выпуск» — Hostinger не подхватил новую версию: в hPanel у сайта → Git → Deploy, затем очистить кэш CDN.
   Когда всё снова работает, issue закроется само с комментарием «Восстановлено». Одно и то же письмо дважды не придёт.
3. **Письмо по понедельникам о битых ссылках** — исправить ссылки в текстах и опубликовать.

Проверки идут каждые 30 минут. Если 60 дней не было ни одной правки в репозитории, GitHub отключает расписание проверок и публикаций — тогда на вкладке Actions нужно нажать «Enable workflow» (или просто сделать любую правку).

## Если на сайте снова старая версия

Откройте `https://bukiski-hram.net/build-info.json`: там время сборки. Если оно свежее, а страница старая — очистите кэш в hPanel (панель сайта → «Kešas» → «Išvalyti laikinąją atmintį»). Если старое — выпуск не дошёл до хостинга: см. пункт 1 выше. Кэш насовсем не отключайте.

## Копии

- Исходники — в GitHub (`main`).
- Готовый сайт целиком — ветка `hostinger-production` в GitHub, с историей всех выпусков. Откат = `git revert` в `main`, остальное сделает автоматика.
- Копии Hostinger — hPanel → сайт → Files → Backups: делаются ежедневно (проверено 12.10.2026), восстанавливаются и скачиваются там же. Раз в месяц полезно убедиться, что они свежие.
- Расписание — в каждом выпуске (`data/services.json`) и в еженедельной копии хостинга .org.

## Раз в неделю (5 минут)

Вкладка Actions обоих репозиториев — нет ли красного; открытые issue «Мониторинг»; расписание на сайте совпадает с календарём.

## Раз в месяц

Открыть главную и расписание с телефона; заглянуть в Search Console; убедиться, что копии Hostinger делаются; если месяц не было правок — сделать любую, чтобы автоматика не отключилась.
