# Развёртывание и перенос доменов

Существующие проекты и домены этой работой не изменены. Для тестовой публикации создан отдельный публичный репозиторий `Maksimas-win/bukiski-parish-next` по поручению владельца. Тестовый адрес: `https://maksimas-win.github.io/bukiski-parish-next/`. Custom domain и DNS действующих сайтов не меняются.

## Новый репозиторий

Создайте пустой репозиторий и загрузите содержимое исходного проекта, включая `.github`, `assets`, `content`, `scripts`, `tests` и шаблон `index.html`. Не загружайте промежуточные `work/`, локальные `.env` или ZIP-архив проекта внутрь самого репозитория. `dist/` генерируется в CI. Workflow Verify проверяет изменения и сохраняет архив собранного сайта. Автоматической замены действующего сайта нет.

Официальные действия GitHub проверены по [документации Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages), [setup-node](https://github.com/actions/setup-node) и [upload-artifact](https://github.com/actions/upload-artifact). Использованы поддерживаемые major-теги; Dependabot предлагает их обновления. Для более строгой политики поставки можно закрепить конкретные проверенные SHA действий.

## Предпочтительный основной хостинг

Статический Apache-хостинг, в том числе Hostinger, позволяет сохранить нынешние `/ru/history.html`, `/lt/contacts.html` и аналогичные адреса.

1. Собрать проект командой `npm run check`.
2. Загрузить **содержимое `dist/`** в отдельную тестовую директорию/поддомен. Включить копирование скрытых `.htaccess` и `.nojekyll`.
3. Проверить работу `mod_headers`, `mod_rewrite`, HTTPS и настоящих 404 на конкретном тарифе. На Nginx `.htaccess` не применяется: его правила должен перенести администратор в конфигурацию сервера.
4. Оставить `PRODUCTION=false` до проверки прихода. Noindex препятствует индексации, но не закрывает доступ: для приватного просмотра включить защиту хостинга.
5. Заполнить `content/release.json`. Для индексируемой версии задать `SITE_ORIGIN=https://bukiski-hram.org`, `BASE_PATH=` и `PRODUCTION=true`, затем повторить сборку и загрузку.
6. По желанию включить прямую выдачу документов: `DOCUMENT_DELIVERY=direct` (см. [DOCUMENTS.md](DOCUMENTS.md)). Сначала убедиться командой `curl -I`, что хостинг отдаёт заголовок `X-Robots-Tag` для PDF/DOC.

`.htaccess` содержит CSP, ограничение встраивания, nosniff, Referrer-Policy, Permissions-Policy, правила кэширования, точечные перенаправления старых путей и 404. Кэширование устроено так: HTML, JSON, календарь и vCard всегда перепроверяются (`no-cache`), поэтому новое расписание видно сразу; стили, скрипты и шрифты кэшируются на год, потому что их адреса содержат хеш выпуска (`?v=…`) и меняются при каждом изменении; изображения — на 30 дней. HTTPS и сертификат включаются средствами хостинга; HSTS следует включать только после проверки HTTPS всех затронутых доменов.

## GitHub Pages

1. В новом репозитории выбрать Settings → Pages → GitHub Actions.
2. Запустить workflow **Deploy test preview to GitHub Pages**.
3. Оставить origin `https://maksimas-win.github.io`, base path `/bukiski-parish-next`.
4. Workflow жёстко задаёт `PRODUCTION=false`: включение индексации через форму запуска недоступно. Для основного запуска требуется отдельное согласованное изменение конфигурации и заполненный release-файл.

Тот же workflow запускается по расписанию каждые шесть часов (03:23, 09:23, 15:23, 21:23 UTC) с адресом по умолчанию. Перед сборкой он загружает свежее расписание из приходского источника — адрес берётся из переменной репозитория `SCHEDULE_SOURCE_URL`, по умолчанию `https://bukiski-hram.org/data/services.json`. Если источник недоступен или не проходит проверку, запуск по расписанию завершается ошибкой и опубликованная версия остаётся прежней; при ручном запуске публикуется снимок из репозитория с предупреждением в журнале. GitHub отключает запуски по расписанию в репозитории, где 60 дней не было активности; тогда их нужно включить заново на вкладке Actions. Запуски по расписанию работают только из основной ветки.

На каждой тестовой HTML-странице установлен `meta robots=noindex,follow`. Это основная мера для проектного URL Pages: файл `/bukiski-parish-next/robots.txt` не заменяет robots.txt в корне домена, который читают поисковые системы. Noindex не ограничивает доступ по ссылке и не скрывает публичный репозиторий от поиска GitHub.

Восстановленные PDF/DOC исключены из статического экспорта. Вместо прямых файлов публикуются 12 HTML-страниц загрузки (RU/LT/EN) с `noindex,nofollow`. Скачивание исходного документа выполняется в браузере; для него нужен JavaScript. Предыдущие прямые адреса возвращают 404. После deploy отдельный этап workflow проверяет HTTP-ответы, noindex и контрольные суммы опубликованных документов. См. [DOCUMENTS.md](DOCUMENTS.md).

Префикс проектного сайта учитывается в навигации, изображениях, canonical, hreflang и скачиваемых файлах. Домен не меняется workflow: DNS и custom domain подключаются отдельно. [GitHub Pages — статический хостинг](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site): обработчика записок на нём нет. Доступность Pages для приватного репозитория зависит от плана GitHub.

На Pages старые `.net`-пути, если их открыть на новом домене, доступны как HTML-копии с canonical. Это **ответ 200, не HTTP 301**. `.htaccess`, `_redirects` и `_headers` GitHub Pages не исполняет. Настоящие перенаправления старого домена должны работать у его провайдера либо на внешнем прокси. HTML meta-refresh не используется как подмена 301.

## Cloudflare Pages как дополнительный вариант

В сборке есть `_headers` и `_redirects`, поддерживаемые [Cloudflare](https://developers.cloudflare.com/pages/configuration/headers/). Однако [Cloudflare Pages автоматически убирает `.html` из адресов](https://developers.cloudflare.com/pages/configuration/serving-pages/). Этот проект сохраняет существующие `.html` canonical, поэтому Cloudflare Pages не является рекомендуемым вариантом без дополнительной настройки Worker/маршрутов и согласованного изменения canonical. Не считать наличие двух конфигурационных файлов завершённой проверкой этой платформы.

## Переключение .net → .org

`content/migration.csv` — согласуемая таблица каждого обнаруженного URL. `deploy/old-domain.htaccess` устанавливается **только на bukiski-hram.net**, после готовности целевых страниц. Файл создаётся сборкой из `origin` и `basePath` в `content/settings.json` и не зависит от адреса, для которого собирается тестовая версия: правила всегда ведут на основной домен. Перед установкой всё равно откройте файл и убедитесь, что во второй строке указан нужный адрес. Если старый сайт остаётся в Hostinger Website Builder, он может не давать доступа к `.htaccess`; тогда нужны поддерживаемые редиректы конструктора, отдельный веб-хостинг старого домена либо правила на прокси. Применимость проверяется в кабинете владельца.

Порядок переноса:

1. Сохранить резервную копию действующего `.org` и экспорт конструктора `.net`. Все четыре прежних недоступных документа уже сохранены в `assets/documents/`; проверить их контрольные суммы по реестру.
2. Проверить новый сайт на тестовом адресе, особенно услуги, телефоны, локализации и банковские реквизиты.
3. Перенести в этот репозиторий генератор `data/services.json` из репозитория действующего `.org` (импорт Google-календаря) или оставить его работать отдельно под другим адресом. Пока расписание берётся с `bukiski-hram.org/data/services.json`, замена сайта на этом домене без переноса генератора остановит обновление расписания.
4. Опубликовать новую `.org`-версию, проверить целевые страницы на ответ 200.
5. Включить точечные 301 на старом домене, включая HTTP/HTTPS и www-варианты.
6. Проверить реальные коды ответа, отсутствие циклов, сохранение неизвестных 404 и новые canonical.
7. Обновить Search Console и sitemap, наблюдать за 404 и индексацией. Сохранять старый домен и его перенаправления длительно.

Примеры обязательной проверки: `/raspisanie-bogosluzhenij` → `/ru/schedule.html`, `/podat-zapisku` → `/ru/notes.html`, одна длинная статья RU и одна статья LT. Не направлять все удалённые URL на главную: смысловое соответствие сохраняется в карте миграции.

Откат: вернуть предыдущий статический выпуск `.org` и отменить правила старого домена. Сохранённые архивы и Git-история позволяют сделать это без потери исходных материалов. Настройки DNS и редиректы в этой задаче не применялись.
