# Архитектура и безопасность

Сайт генерируется в готовый HTML модулями Node.js. Сторонних npm-пакетов, базы данных, авторизации посетителей и клиентского фреймворка нет. Такой вариант подходит небольшому приходу: страницы можно разместить на обычном хостинге, обновления просматриваются в GitHub, а сайт остаётся читаемым при отключённом JavaScript.

## Разделение ответственности

| Где | Что |
|---|---|
| `content/locales.json` | Тексты интерфейса и основных разделов на RU/LT/EN |
| `content/settings.json` | Домен, адрес, телефон, реквизиты, ссылки на внешние источники, режим выдачи документов |
| `content/source-*.json` | Страницы, изображения, ссылки и документы двух прежних сайтов. Архив переноса, а не редакционный текст |
| `content/original-services.json` | Снимок расписания из приходского календаря |
| `index.html` | Оболочка HTML-документа с заполнителями `{{…}}` |
| `styles/*.css` | Стили. Сборка объединяет файлы по алфавиту в один `assets/css/site.css` |
| `assets/js/domain.js` | Правила данных без обращения к DOM и сети: расписание, имена, поиск, iCalendar. Используется и сборкой, и браузером, и тестами |
| `assets/js/ui/`, `features/` | Клиентские модули. `app.js` подключает модуль только на тех страницах, где есть его разметка |

Сборка (`scripts/build.mjs`) — короткий сценарий, который вызывает модули из `scripts/lib/`:

- `site.mjs` читает содержимое и окружение, проверяет их и даёт страницам общие функции (`url`, `canonical`, `route`);
- `catalog.mjs` сопоставляет каждой исходной странице новый адрес и решает, нужна ли ей отдельная архивная копия;
- `html.mjs` — шаблоны с экранированием по умолчанию: любая подставленная строка экранируется, готовую разметку нужно явно пометить `raw()`;
- `layout.mjs`, `components.mjs`, `pages/*.mjs` — оболочка документа, общие фрагменты и по модулю на тип страницы;
- `outputs.mjs` — sitemap, robots, `.htaccess`, `_headers`, `_redirects`, календарь, vCard, поисковый индекс.

Каждый основной раздел имеет постоянные RU/LT/EN-адреса. Архив не выдаётся за новый перевод. PL, DE и UK сохраняются как исходные языки. При добавлении языка нужны словарь, вычитка, новые основные маршруты и проверка hreflang.

### Адреса исходных страниц

У каждой исходной страницы есть `target` (куда ведёт старый адрес) и `archive` (где читается сохранённый текст). Для статей библиотеки это одна и та же страница. Отдельная копия в `/archive/` создаётся только там, где раздел переписан заново (главная, расписание, контакты и т. п.), чтобы прежняя формулировка не пропала. Старые пути `.net` дополнительно доступны как копии с правильным canonical: статический хостинг не умеет отдавать HTTP 301, а на Apache их заменяют правила `.htaccess`.

### Версии стилей и скриптов

Сборка вычисляет общий хеш стилей и скриптов и добавляет его к каждому адресу: `site.css?v=…`, `app.js?v=…` и ко всем `import` внутри модулей. Поэтому браузер никогда не смешивает файлы двух выпусков, а на Apache их можно кэшировать надолго. HTML и данные всегда перепроверяются.

## Расписание

Источник имеет версию схемы, часовой пояс, дату создания, дату последней успешной синхронизации и массив событий. Событие содержит устойчивый ID, дату, время, абсолютный `start` с UTC-смещением и заголовок в трёх языках. Статус отмены подавляет одноимённую запись. События без определённого времени не представляются как точное расписание. Отметка «праздник» берётся из поля `feastType` источника; сайт сам праздники не вычисляет.

Сборка проверяет совпадение `start`, локальной даты и времени в Europe/Vilnius. Это важно в ночь перевода часов. Все будущие службы находятся в HTML. Браузер ничего не загружает: он скрывает уже начавшиеся службы, подписывает «сегодня» и «завтра» по календарю Вильнюса и показывает предупреждение, если снимок старше `scheduleMaxAgeHours` из настроек.

Файлы календаря используют UTC, перенос строк по байтам и стабильные UID. У событий есть только начало: в источнике нет времени окончания, и сайт его не придумывает. Скачанный файл — снимок, а не подписка; подписаться можно по ссылке на приходской календарь.

Тестовая публикация каждые шесть часов загружает свежий снимок из `https://bukiski-hram.org/data/services.json`, проверяет его и публикует сайт заново (см. [DEPLOYMENT.md](DEPLOYMENT.md)). Неудачная загрузка или проверка оставляет опубликованную версию без изменений. Этот JSON сейчас создаёт действующий сайт `.org` из Google-календаря прихода. **При переносе домена генератор нужно перенести вместе с ним**, иначе источник исчезнет; новый сайт не должен считать собственную опубликованную копию свежим источником.

## Защита

- В страницы не вставляются теги из старых сайтов: текст экранируется шаблонами, изображения берутся из локального архива.
- Клиентский код создаёт элементы и задаёт `textContent`; нет `innerHTML`, `eval`, inline-скриптов и inline-стилей. Это проверяет `tests/client.test.mjs`.
- Разрешены только HTTPS-ссылки без имени пользователя и пароля.
- CSP ограничивает загрузки собственным источником, запрещает плагины, изменение base URI и обычную отправку форм. Единственное исключение — `connect-src` для сервиса приёма записок: его адрес берётся из `settings.notes.endpoint`, тест проверяет, что других сторонних адресов в политике нет. На Apache добавляются `frame-ancestors`, `nosniff`, Referrer-Policy и Permissions-Policy.
- На GitHub Pages HTTP-заголовки не управляются этими файлами: работает meta-CSP, но защита от встраивания через `frame-ancestors` требует серверного заголовка. Это ограничение нельзя решить добавлением директивы в meta.
- Нет автоматических карт, внешних шрифтов, аналитики и рекламных cookies. Внешние сервисы открываются осознанным переходом.
- В `localStorage` хранятся только настройки чтения: оформление, размер текста, контрастность. Маленький скрипт `theme-init.js` применяет их до первой отрисовки, чтобы тёмная тема не мигала светлой. Имена записки никогда не попадают в URL, журнал или хранилище браузера; на сервер они уходят только по нажатию «Отправить» (см. ниже).
- Сетевых запросов из браузера три, все по действию посетителя и без cookies: поисковый индекс библиотеки и страница-контейнер документа (оба к собственному сайту) и отправка записки в сервис приёма.

## Оформление

Шрифты — Source Serif 4 Display для заголовков и Source Sans 3 для текста, те же, что на действующем сайте прихода; файлы лежат в `assets/fonts/` с лицензиями. Цвета взяты у самого храма: бордо приходской эмблемы, синева куполов, светлый кирпич стен, позолота крестов. Все пары «текст — фон» светлой и тёмной темы проверяются на контраст не ниже 4,5:1, а размер текста — не меньше 13 px (`tests/design.test.mjs`). Килевидная арка в обрамлении фотографии и плашек с датами повторяет форму окон и закомар храма.

## Записки и GDPR

Записку можно распечатать, скачать или скопировать без всякой отправки. По решению прихода (11 октября 2026 г.) сохранена и онлайн-подача, как на прежнем bukiski-hram.net: та же форма Formspree (`settings.notes.endpoint`), те же названия полей, поэтому письма в почту прихода выглядят как раньше.

Как устроена отправка:

- запрос уходит только по нажатию «Отправить» и только при отмеченном согласии; без JavaScript отправка недоступна, обычная отправка формы запрещена CSP (`form-action 'none'`);
- передаются вид записки, имена, по желанию имя подателя, e-mail и пояснение, а также адрес страницы без параметров; cookies не отправляются;
- скрытое поле `_gotcha` отсекает простых ботов (механизм Formspree);
- после успешной отправки форма очищается; при ошибке имена остаются, чтобы можно было повторить;
- имена не попадают в URL, хранилище браузера, журналы сайта или репозиторий.

Имена в религиозном контексте могут относиться к специальной категории данных ([статья 9 GDPR](https://eur-lex.europa.eu/eli/reg/2016/679/oj)); согласие подателя не является автоматически согласием других названных людей. Formspree — обработчик данных в США. Перед публичным запуском приход должен указать на странице конфиденциальности оператора, срок хранения писем с записками и порядок обращений, а также проверить лимит отправок на своём тарифе Formspree. Это техническое описание, а не юридическое заключение.

Чтобы отключить онлайн-подачу, удалите `notes` из `content/settings.json`: кнопка отправки не появится, а сторонний адрес исчезнет из CSP.

## Публичный контракт данных приложения

Сборка создаёт `/api/v1/bootstrap.json` — небольшой версионированный JSON для
официального приложения прихода. Он содержит только разрешённые публичные
сведения: названия на поддерживаемых языках, адрес, телефон, координаты,
основные маршруты сайта и не более двенадцати ближайших служб с подтверждённым
временем. Контакты и расписание берутся из тех же проверяемых источников, что и
страницы сайта; приложение не должно хранить их отдельную редактируемую копию.
Для расписания также передаются предел допустимого возраста снимка и признак
`stale`: приложение обязано заметно предупредить пользователя при устаревших
данных, но может показать последний достоверный снимок. Подтверждённые приходом
примечания к отдельным службам передаются вместе с ними.

Файл формируется через явный белый список полей. В него не попадают адреса
обработчиков форм и ИИ, банковские реквизиты, ID календаря, исходные архивные
URL, сообщения посетителей или секреты. Текущая схема имеет `schemaVersion: 1`.
Её существующие поля нельзя удалять, переименовывать или менять по смыслу без
нового пути и новой версии API. Будущий Node.js/Express-сервис должен сохранить
этот контракт, чтобы обновление сервера не потребовало переделки приложения.

## Развитие

1. Завершить языковую и пастырскую вычитку, затем подключить регулярную редакционную работу через pull requests.
2. Перенести утверждённый календарный источник в отдельный процесс с наблюдением за ошибками и сохранением последнего достоверного снимка.
3. При росте числа редакторов подключить CMS, которая создаёт изменения файлов в Git; публичная часть может остаться статической.
4. Добавлять переводы статей по одной, связывая конкретные эквиваленты, без автоматического смешения языков.
5. При росте числа записок — рассмотреть собственный обработчик приёма вместо Formspree, с хранением в ЕС и удалением по сроку.
