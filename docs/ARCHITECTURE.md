# Архитектура и безопасность

Сайт генерируется в готовый HTML небольшим модулем Node.js. Сторонних npm-пакетов, базы данных, авторизации посетителей и клиентского фреймворка нет. Такой вариант подходит небольшому приходу: страницы можно разместить на обычном хостинге, обновления просматриваются в GitHub, а сайт остаётся читаемым при отключённом JavaScript.

## Разделение ответственности

`content/locales.json` содержит редакционные тексты; `settings.json` — приходские реквизиты и домен. Источники хранятся отдельно от нового текста. `index.html` задаёт HTML-документ; сборщик заполняет разделы, метаданные и навигацию. `assets/css/site.css` содержит все стили. `assets/js/app.js` отвечает за меню, настройки чтения, фильтр библиотеки, обновление вида расписания и локальную записку. `domain.js` содержит проверяемые правила данных.

Каждый основной раздел имеет постоянные RU/LT/EN-адреса. Архив не выдаётся за новый перевод. PL, DE и UK сохраняются как исходные языки и могут стать полноценными локализациями в следующей версии. При расширении языка нужны словарь, вычитка, новые основные маршруты и проверка hreflang.

## Расписание

Источник имеет версию схемы, часовой пояс, дату создания, дату последней успешной синхронизации и массив событий. Событие содержит устойчивый ID, дату, время, абсолютный `start` с UTC-смещением и заголовок в трёх языках. Статус отмены подавляет одноимённую запись. События без определённого времени не представляются как точное расписание.

Сборка проверяет совпадение `start`, локальной даты и времени в Europe/Vilnius. Это важно в ночь перевода часов. Файл ICS использует UTC, перенос строк по байтам и стабильные UID. Скачивание ICS — снимок, не автоматическая подписка. Подписаться на актуальный приходской источник можно через ссылку на календарь.

Импорт расписания ручной и атомарный: неудачная загрузка или проверка не уничтожает последний рабочий файл. После переноса домена источник должен жить отдельно либо данные должны утверждаться редактором в Git. Новый сайт не должен считать свою собственную копию внешним обновлённым источником.

## Защита

- В исходный HTML не вставляются теги из старых сайтов: текст экранируется, изображения берутся из локального архива.
- Динамический интерфейс использует `textContent`; нет `innerHTML`, `eval`, inline-скриптов или inline-стилей.
- Разрешены только HTTPS-ссылки без имени пользователя и пароля. Имена записки никогда не попадают в URL, журнал, localStorage или запрос к серверу.
- CSP ограничивает загрузки собственным источником, запрещает плагины, изменение base URI и отправку форм. На Apache добавляются `frame-ancestors`, `nosniff`, Referrer-Policy и Permissions-Policy.
- На GitHub Pages HTTP-заголовки не управляются этими файлами: работает meta-CSP, но защита от встраивания через `frame-ancestors` требует серверного заголовка. Это ограничение нельзя решить добавлением директивы в meta.
- Нет автоматических карт, внешних шрифтов, аналитики и рекламных cookies. В localStorage хранятся только выбранные настройки чтения. Внешние сервисы открываются осознанным переходом.

## Записки и GDPR

Имена в религиозном контексте могут относиться к специальной категории данных. [Статья 9 GDPR](https://eur-lex.europa.eu/eli/reg/2016/679/oj) требует отдельного основания; согласие подателя не является автоматически согласием других названных живых людей. Исключение для религиозной организации также имеет условия. Поэтому данная версия готовит записку только на устройстве посетителя.

До включения сетевой отправки приход должен определить оператора, основания обработки, состав данных, доступ сотрудников, сроки удаления, процессоров и порядок обращений. Затем нужен отдельный серверный обработчик с HTTPS, проверкой схемы, ограничением длины и частоты запросов, защитой от межсайтовой отправки, приватным хранением и удалением по сроку. Имена не должны попадать в GitHub Issues, публичный репозиторий, аналитику или журналы ошибок. В этой версии API приёма отсутствует; кнопки отправки и фиктивных сообщений об успешной доставке нет.

Страница конфиденциальности содержит правдивое описание текущего режима и явно обозначает сведения о хостинге и операторе, которые приход ещё должен заполнить. Это подготовка технических условий, а не заявление о полном юридическом соответствии.

## Развитие

1. Завершить языковую и пастырскую вычитку, затем подключить регулярную редакционную работу через pull requests.
2. Перенести утверждённый календарный источник в отдельный процесс с наблюдением за ошибками и сохранением последнего достоверного снимка.
3. При росте числа редакторов подключить CMS, которая создаёт изменения файлов в Git; публичная часть может остаться статической.
4. Добавлять переводы статей по одной, связывая конкретные эквиваленты, без автоматического смешения языков.
5. Если необходим онлайн-приём записок — выделить защищённый сервис с самостоятельной оценкой правовых и организационных условий.
