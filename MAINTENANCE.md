# Обслуживание сайта bukiski-hram.net

Этот репозиторий обслуживает домен **bukiski-hram.net** (основной сайт прихода на шести языках). Домен **bukiski-hram.org** обслуживается отдельным репозиторием [bukiski-hram-org](https://github.com/Maksimas-win/bukiski-hram-org) — у него свой `MAINTENANCE.md`. Автоматический мониторинг обоих сайтов живёт здесь (см. раздел 5).

Короткая памятка для владельца — в [docs/OWNER.md](docs/OWNER.md).

## 1. Как изменения попадают на сайт

```
правка в main  →  GitHub Actions «Export production site for Hostinger» (production.yml)
               →  сборка + npm run check  →  ветка hostinger-production  →  Hostinger (Git-развёртывание)
```

- Ветка `main` — исходники. Ветка `hostinger-production` — готовые файлы сайта; её наполняет только workflow, руками в неё не пишут.
- Workflow запускается при каждом изменении `main`, вручную (Actions → Run workflow) и по расписанию четыре раза в сутки (03:43, 09:43, 15:43, 21:43 UTC) — чтобы подтянуть свежее расписание.
- Hostinger забирает ветку `hostinger-production` сам (Git-развёртывание в hPanel, аккаунт u736200154). Обычно сайт обновляется в течение минуты после записи в ветку.
- Тестовая копия для просмотра изменений: GitHub Pages (`pages.yml`, адрес `https://maksimas-win.github.io/bukiski-parish-next/`), всегда с `noindex`.
- Правки делаются через pull request: `verify.yml` прогоняет `npm run check` в обоих режимах выдачи документов. В `main` попадает только то, что прошло проверки.

Процесс публикации не дублировать: второй канал выкладки будет перезаписывать сайт.

## 3. Расписание

- Источник расписания — приходской Google-календарь. Сайт .org читает его каждый час и публикует фид `https://bukiski-hram.org/data/services.json`; этот сайт забирает фид при каждой сборке (`npm run schedule:sync`, адрес в `production.yml`). Церковный календарь (память святых, чтения) приходит из того же фида.
- Дата, которую показывает сайт и помощник («Источник обновлён»), — это время последнего **успешного** чтения Google-календаря на .org (`source.lastSuccessAt`), а не дата сборки. Если календарь недоступен, прежний снимок остаётся, а дата стареет; старше 48 часов — страница расписания показывает предупреждение, помощник советует позвонить, мониторинг открывает issue.
- Служба, которой в календаре нет или она стоит без времени: добавьте запись в `content/schedule-additions.json` (дата, время по Вильнюсу, название на 6 языках, пояснение). Когда в календаре появится служба с тем же днём и временем, сайт возьмёт её из календаря и сохранит только пояснение; запись можно удалить. Лучший путь — всё же поставить службе время в Google-календаре: тогда она появится и на .org.
- Отменённая служба: отметьте её отменённой в Google-календаре — фид помечает `cancelled`, сайт её не показывает.
- Переход на зимнее/летнее время учитывается: время хранится с явным смещением, сборка проверяет совпадение с часами Вильнюса.

## 4. Где смотреть результаты публикации и ошибки

- GitHub → **Actions**: `Export production site for Hostinger` — каждая выкладка; `Site monitor` — проверки сайтов; `Verify` — проверки pull request.
- При падении любого workflow GitHub присылает письмо на почту аккаунта владельца (стандартные уведомления GitHub о неудачных запусках).
- Что реально опубликовано: `https://bukiski-hram.net/build-info.json` — время сборки, версия ресурсов, время данных календаря; должно совпадать с `build-info.json` в ветке `hostinger-production`.

## 5. Автоматические проверки (мониторинг)

Workflow `.github/workflows/site-monitor.yml`, скрипты `scripts/monitor/`. Только читает сайты, ничего не публикует.

| Проверка | Когда | Что именно |
|---|---|---|
| Здоровье обоих сайтов | каждые 30 минут (:07 и :37) | Главные и ключевые страницы обоих сайтов отвечают 200 и содержат основной блок и скрипт помощника; HTML, CSS и JS относятся к одной версии (`build-info.json` / `version.json`); `www.` перенаправляется; sitemap и фид расписания доступны; данные календаря не старше 48 часов |
| Выпуск .net | после каждого успешного `production.yml` | Ждёт до ~6 минут, пока Hostinger отдаст версию из `hostinger-production`; потом обычная проверка |
| Ссылки и ресурсы | понедельник 04:23 UTC | Все страницы из sitemap обоих сайтов, все внутренние ссылки, картинки, стили и скрипты; последовательно, с паузами |

Защита от ложных тревог: тайм-аут 15 с на запрос; сетевая ошибка, тайм-аут, 5xx или 404 повторяется один раз через 20 с (во время развёртывания файл может на мгновение отсутствовать); если страницы сайта не совпадают по версии с его маркером (`build-info.json` / `version.json`), сайт перепроверяется с нуля через 90 с — идущая в этот момент публикация не считается сбоем; в отчёт попадает только повторная неудача.

Уведомления: при подтверждённом сбое в этом репозитории открывается **issue с меткой `monitoring`**, назначенный владельцу (GitHub присылает письмо), и этот запуск отмечается как неудачный (ещё одно письмо). Пока сбой тот же — ни новых issue, ни комментариев. Когда проверки снова проходят, в issue добавляется комментарий «Восстановлено» и он закрывается. Имитация сбоя для проверки канала: Actions → Site monitor → Run workflow → `simulate: failure`; следующий обычный запуск закроет issue.

Первый ручной прогон проверки ссылок 12.10.2026: .net — 161 страница, 456 ссылок и ресурсов; .org — 32 страницы, 88 ссылок и ресурсов; единственная «находка» оказалась ошибкой самого разбора (ссылка на Google Maps с запятыми в координатах), исправлено в тот же день (#22), issue закрыт повторным прогоном. Второй прогон застал развёртывание Hostinger (две страницы на секунды отвечали 404) — добавлен повтор запроса при 404 (#23); третий прогон (18:41 UTC) чистый, issue закрыт автоматически.

Проверено 12.10.2026 имитацией сбоя: первый запуск с `simulate: failure` создал issue [#20](https://github.com/Maksimas-win/bukiski-parish-next/issues/20), назначенный владельцу, и завершился красным; повторный такой же запуск не создал ни issue, ни комментария; обычный запуск после него добавил комментарий «Восстановлено» и закрыл issue. Доставка писем GitHub на почту владельца не проверялась изнутри — владелец подтверждает получение письма об issue #20.

Ограничения планировщика GitHub: запуски по расписанию могут задерживаться на минуты (в часы пик — дольше), минимальный интервал 5 минут, а после 60 дней без коммитов в репозитории расписание отключается — тогда его нужно включить заново на вкладке Actions (это касается и выкладки по расписанию).

### Если пришла тревога

1. Откройте issue: в нём перечислены проверки, которые не прошли, и ссылка на запуск.
2. `HTTP 5xx`, `timeout`, `HTTP 0` на обоих сайтах — скорее всего, проблема у Hostinger: проверьте статус хостинга в hPanel и `https://statuspage.hostinger.com/`. Ничего не переразвёртывайте.
3. `net:release` — Hostinger не забрал новую ветку: в hPanel → сайт → Git → Deploy (повторить развёртывание), затем очистить кэш CDN.
4. `*:schedule-freshness` — данные календаря старше 48 часов: посмотрите последние запуски `Deploy to Hostinger` в репозитории .org (там читается Google-календарь); если Google недоступен, ждать; если ошибка в календаре — исправить запись в календаре и запустить workflow вручную.
5. `page does not reference version` — главная и внутренние страницы разных версий: см. раздел 8.
6. `*:link` в понедельничном отчёте — битая ссылка или ресурс; исправить в исходниках и опубликовать.

## 7. Восстановление и откат

- **Откатить неудачный выпуск**: в `main` сделать `git revert <коммит слияния>` и отправить в GitHub — workflow соберёт и опубликует прежнюю версию. Это единственный штатный путь; ветку `hostinger-production` руками не трогать.
- **Восстановить сайт после потери файлов на хостинге**: в hPanel → сайт → Git → Deploy повторно развернуть ветку `hostinger-production` (или запустить `production.yml` вручную — он перезапишет ветку свежей сборкой). При полной потере аккаунта: создать Git-развёртывание ветки `hostinger-production` заново, проверить, что `.htaccess` отдаёт заголовки (раздел 5 мониторинга это покажет).
- **Восстановить из копии Hostinger**: hPanel → сайт → Files → Backups → выбрать дату → «Atkurti failus» (только если ветка недоступна; потом всё равно сверить с веткой).
- Локальная проверка любого снимка: `git archive origin/hostinger-production | tar -x -C /tmp/site && (cd /tmp/site && python3 -m http.server 8000)`.

## 8. Если снова видна старая версия

Наблюдалось при переезде с конструктора: CDN Hostinger отдавал закэшированную главную, а новые внутренние адреса в кэше не было. Сейчас HTML, sitemap, robots и JSON публикуются с `Cache-Control: no-cache` (CDN их не кэширует — `x-hcdn-cache-status: DYNAMIC`), а CSS/JS имеют версию в адресе, поэтому старая и новая версии смешаться не должны.

Если всё же видите старое:
1. Откройте `https://bukiski-hram.net/build-info.json` — там время сборки. Сравните с последним запуском `production.yml` и коммитом в `hostinger-production`.
2. Если ветка новая, а сайт старый — Hostinger не развернул ветку: hPanel → Git → Deploy.
3. Если `build-info.json` новый, а страница старая — очистите кэш: hPanel → сайт (Valdymo skydas) → блок «Kešas» → «Išvalyti laikinąją atmintį» (Purge cache); там же «Peržiūra be kešavimo» открывает сайт без кэша. Затем проверьте страницу в режиме инкогнито. 12.10.2026 кэш обоих сайтов очищен после выпусков.
4. Кэш не отключайте навсегда: настройки кэширования в `.htaccess` рассчитаны на CDN, менять их без причины не нужно.

## 9. Регламент

**После каждого изменения**: дождаться зелёного `production.yml`, затем зелёного `Site monitor` (режим release); открыть изменённую страницу на компьютере и телефоне; при изменении расписания — сверить с Google-календарём.

**Еженедельно**: посмотреть вкладку Actions (нет ли красных запусков), открытые issue с меткой `monitoring`, понедельничный отчёт о ссылках; убедиться, что в hPanel есть свежая копия Hostinger.

**Ежемесячно**: открыть главную и расписание на телефоне; проверить, что расписание по датам совпадает с календарём; проверить `https://bukiski-hram.net/sitemap.xml` и Search Console (ошибки индексации); сделать коммит, если 60 дней не было изменений, чтобы не отключилось расписание workflow; просмотреть предложения Dependabot по версиям actions.

## 10. Какие доступы нужны владельцу

Без самих секретов — только где они живут:

- **GitHub**: владелец обоих репозиториев (слияние PR, запуск workflow, issue мониторинга, уведомления на почту аккаунта).
- **Hostinger hPanel, аккаунт u736200154** (план Business Web Hosting до 07.11.2028; на нём же `bukiski-hram.org`, `bukiski-hram.com`, `bukiski.lt`, `bukiskihram.lt`): Git-развёртывание ветки `hostinger-production` (блок «Prisijungta su GitHub» на панели сайта показывает последний деплой, ветку и коммит), очистка кэша, копии, домен и SSL.
- **Google-календарь прихода** (расписание): права редактора.
- **Formspree** (форма записок, адрес в `content/settings.json` → `notes.endpoint`): кабинет, куда приходят записки.
- **Регистратор доменов / DNS**: записи обоих доменов (в этом репозитории не меняются).

Секретов в этом репозитории нет; публикация .net не требует паролей (Hostinger сам читает ветку).
